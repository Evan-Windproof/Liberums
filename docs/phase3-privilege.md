# 从 Ring 0 进入 Ring 3

## 为什么需要两个特权级

C 中“不要访问别人的指针”不是隔离。Ring 3 把不可信程序放在 CPU 权限较低的环境中：
特权指令被拒绝，分页也根据当前级别检查是否可以访问 supervisor 页面。
内核位于 Ring 0，负责建立、校验和撤销这些边界。

## GDT、选择子与 CPL/DPL/RPL

选择子的高位是 GDT 索引，低两位是 RPL；GDT 描述符中的 DPL 给出允许的特权级。
当前执行代码 CS 的低两位给出 CPL。数值 0 权限最高，3 用于用户。

| 选择子 | 用途 | DPL / RPL |
| --- | --- | --- |
| 0x08 | 内核代码 | 0 / 0 |
| 0x10 | 内核数据与 SS0 | 0 / 0 |
| 0x1b | 第 3 项用户代码 | 3 / 3 |
| 0x23 | 第 4 项用户数据、栈 | 3 / 3 |
| 0x28 | 第 5 项 TSS | 0 / 0 |

用户不能用普通远跳转把 CS 改成 0x08 提权。段访问仍受 CPL/DPL/RPL 的硬件检查。
所有代码/数据段都是平坦基址零，段机制负责级别，实际内存边界主要由分页控制。

## TSS 提供可信入口栈

用户可以随意修改自己的 ESP，所以内核不能以它作为系统调用栈。
32 位 TSS 的 SS0/ESP0 指定从用户进入 Ring 0 时由 CPU 使用的栈。
`ltr 0x28` 加载任务寄存器；每次切换用户域前更新 ESP0 指向该域 8 KiB 内核栈顶部。
这不是硬件任务调度。这里的上下文和 CR3 全由软件切换。

IOPL 保持 0。TSS I/O bitmap 的偏移 104 超过描述符 limit=103，用户端口 I/O 没有许可，
实际 `outb` 实验得到 #GP。用户 `cli` 也得到 #GP。

## 跨特权级栈帧

从用户执行 `int 0x80` 或发生异常时，CPU 先使用 TSS 切栈，再保存旧用户 SS/ESP：

```text
可信内核栈顶部（ESP0）
    旧 SS             仅 CPL 3 -> 0 时存在
    旧 ESP            仅 CPL 3 -> 0 时存在
    EFLAGS
    CS
    EIP
    CPU 错误码        仅指定异常具有
    入口补齐/vector   汇编统一错误码约定
    pushal 通用寄存器
```

同级 Ring 0 异常没有旧 ESP/SS，不能在它的 52 字节前缀之外读取。
`user_context` 才具有最后两个字段，总计 60 字节；代码先依据保存的 CS 判断来源。
GDB 同时检查保存的用户 CS/SS、现场地址范围及 C handler 当前 ESP，证明并未借用用户栈。
即使用户把 ESP 改为零再执行 ud2，内核也能报告并结束该域。

## iret 与返回安全

第一次进入时，内核构造用户 CS/SS、EIP、ESP、EFLAGS，再 iret；它同时完成外层特权级返回和栈切换。
普通系统调用也使用 iret 恢复保存现场。用户不能提供一份任意内核 iret 帧：
实际帧由 CPU 写入 supervisor 的可信栈，C 还验证域身份和地址空间。

返回前清除 NT（嵌套任务）、VM、IOPL、TF 和 IF，保留算术标志和 DF，固定保留 bit 1。
特别是 NT 不能原样进入内核的 iret，否则可能触发硬件任务返回。用户测试主动设置 NT 和 DF，
yield 后检查 NT 已清除、DF 得到保留；汇编进入 C 前始终 cld。
通用寄存器除 EAX 返回值之外保留；段寄存器每次返回归一化为 0x23，不提供 TLS 语义。

## 最小系统调用 ABI

`int $0x80`，EAX=调用号，EBX=一个标量参数，EAX=返回值。其他通用寄存器保持。

| EAX | 接口 | EBX / 返回 |
| --- | --- | --- |
| 0 | yield | 参数忽略；恢复执行时 EAX=0 |
| 1 | exit | uint32 退出状态；不返回 |
| 2 | log_char | 0..255；成功返回 0，范围错误 -22，额度用尽 -11 |
| 其他 | 未知调用 | -38（ENOSYS） |

负数按 32 位补码返回。没有字符串、用户指针、物理地址或任意函数调用接口，因此没有隐含的
“直接解引用用户指针”路径。新增指针接口前必须另外实现校验与安全复制。
只有 IDT[128] 的 DPL 为 3；普通异常门 DPL 为 0，用户软件 int 3 被硬件拒绝为 #GP，
但 CPU 检测到的异常仍会正常进入相应门。

## 用户异常为什么不会让内核停止

保存 CS 的 RPL 为 3 时，内核确认当前域、CR3、可信栈和用户 SS 后记录故障并终止该域。
它返回调度者，选择另一个 READY 域；不会增加 EIP 来假装恢复。
Ring 0 异常及 NMI/double fault/machine check 继续严格停止，避免把内核损坏伪装成用户错误。

## 扩展寄存器状态

只保存通用寄存器并不足以开放 FPU：另一域可能读到上一域留下的 x87/MMX/SIMD 状态。
本阶段不实现这些扩展状态的保存与恢复。每次进入用户前设置 CR0.TS，用户 x87 指令触发 #NM
并结束该域；未启用的 SSE 功能也可能由 CPU 报 #UD。内核和用户 C 都编译为不使用这些指令。
用户不能执行 CLTS 清除保护。实际 fninit 测试验证 #NM 后另一域仍正常运行。
未来若开放浮点，必须先设计完整扩展状态切换，不能只去掉 TS。

## 当前限制与参考

没有时钟抢占，用户可能无限占用 CPU；没有独立 double-fault 栈、SMP 或异常恢复。
这些都不应被描述为成熟调度器或可强制 CPU 撤销。
设计依据为 [Intel SDM](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html)
Volume 3A 的 Protection、Task Management、Interrupt and Exception Handling 各章，以及 IRET/INT 指令约定。
实现自行编写，实际硬件路径用 QEMU/GDB 检查。
